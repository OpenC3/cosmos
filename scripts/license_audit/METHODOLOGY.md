# Dependency License Audit

`license_audit.py` answers one question, and answers it the same way every
time:

> Does anything OpenC3 COSMOS depends on carry a license we cannot ship under?

Run it:

```bash
scripts/license_audit/license_audit.py            # full audit
scripts/license_audit/license_audit.py --show all # ...and list every package
scripts/license_audit/license_audit.py --self-test
```

Exit status is the point: `0` if nothing was found at or above `--fail-on`
(default `restricted`), `1` if something was, `2` if the audit could not be
completed. That makes it usable as a release gate, not just a report.

## Why this matters here specifically

COSMOS is distributed under the **OpenC3 Builder's License** (`LICENSE.md`), a
source-available license with commercial-use limitations. It is not GPL, and it
cannot be. A GPL or AGPL dependency linked into a shipped container would leave
us with two options, both bad: relicense COSMOS under terms we did not choose,
or distribute in violation. AGPL is worse still, because COSMOS *is* the kind of
software people run as a hosted service, which is exactly the trigger the Affero
clause exists for.

So the tool's default failure threshold is not a style preference. Anything in
the `restricted` bucket is a legal blocker, and the audit is designed to fail
loudly rather than produce a report nobody reads.

## What is audited

**Lockfiles, not manifests.** A manifest says `~> 8.1`; a lockfile says
`8.1.3`, and it says it for the whole transitive closure. Only the closure has
legal meaning, because it is what actually gets installed and shipped. The
lockfiles in scope are listed explicitly in the `MANIFESTS` table in the script:

| Lockfile | Ecosystem | Scope |
| --- | --- | --- |
| `openc3/Gemfile.lock` | Ruby | runtime |
| `openc3-cosmos-cmd-tlm-api/Gemfile.lock` | Ruby | runtime |
| `openc3-cosmos-script-runner-api/Gemfile.lock` | Ruby | runtime |
| `openc3/python/uv.lock` | Python | runtime |
| `openc3-cosmos-init/plugins/packages/openc3-cosmos-demo/uv.lock` | Python | runtime |
| `openc3-cosmos-init/plugins/pnpm-lock.yaml` | JavaScript | runtime |
| `docs.openc3.com/pnpm-lock.yaml` | JavaScript | dev |
| `playwright/pnpm-lock.yaml` | JavaScript | dev |

The table is explicit rather than a glob because **coverage is the part of an
audit that rots**. Someone adds a service, its dependencies are never checked,
and nothing complains. So the tool also scans the repository for every
`Gemfile.lock`, `uv.lock` and `pnpm-lock.yaml`, and fails if it finds one that
is neither in `MANIFESTS` nor deliberately excluded in `IGNORED_MANIFESTS` (with
a stated reason, e.g. "generated by the Ruby LSP extension", "scaffolding for
user-generated plugins"). A new lockfile cannot enter the repo and quietly skip
the audit.

JavaScript dependencies pinned to git, tarballs, or other nonregistry package
sources cannot be checked against an exact registry release. The audit stops
with exit status `2` when it encounters one, so an unsupported source cannot
silently disappear from the package list. These sources need a separate
license review before the audit can be considered complete.

**Runtime vs dev.** Each package is marked `runtime` or `dev`:

- Ruby: reachability through the `Gemfile.lock` spec graph from the non-dev
  entries of `DEPENDENCIES`. Bundler groups are not recorded in the lockfile, so
  the sibling `Gemfile` is parsed for `group :development/:test` blocks — and so
  is the gemspec it pulls in with `gemspec`, because
  `add_development_dependency` entries land in `DEPENDENCIES` looking exactly
  like runtime dependencies.
- Python: reachability from the workspace project's `dependencies`, with
  `dev-dependencies` groups as the dev roots.
- JavaScript: reachability through the pnpm `snapshots` graph from every
  importer's `dependencies` (not `devDependencies`).

The distinction is reported but does not by itself excuse anything: a GPL build
tool is usually fine, but "usually" is a judgement someone should make and write
down, which is what `EXCEPTIONS` is for.

### What is *not* audited, and why

- **Container base images and OS packages** (Alpine, UBI, Valkey, Traefik,
  Versity). Those are not language-level dependencies of our source tree; they
  are covered by the container scanning already configured in `trivy.yaml` and
  `.grype.yaml`, and by the base image vendors' own license manifests.
- **Vendored or copied source.** This tool reads dependency graphs. Source
  copied into the tree carries whatever license it came with and no lockfile
  mentions it; that is a code-review problem, not a dependency-resolution one.
- **`openc3/templates/`**. Those dependencies become the *user's* dependencies
  in a generated plugin, not ours.
- **`examples/`** — sample plugins, not distributed with COSMOS.

## How a license is determined

For every locked package, in order, stopping at the first answer:

1. **Locally installed metadata** — the gemspecs in the local RubyGems store,
   `*.dist-info/METADATA` in the repo's uv virtualenvs,
   `node_modules/.pnpm/*/package.json`. This is the metadata the package's own
   author shipped, it needs no network, and it cannot drift from what a build
   installed.
2. **The package registry** — rubygems.org, pypi.org, registry.npmjs.org,
   queried for the *exact* locked version, concurrently, and cached on disk
   (`~/.cache/openc3-license-audit/licenses.json`). Locked versions are
   immutable, so a cache hit never needs revalidating; `--refresh` discards the
   cache and `--offline` skips the network entirely.
3. **Another published version of the same package** — used only as a labelled
   last resort. Some releases genuinely ship no license metadata at all (a
   `pyproject.toml` with only `license-files`, an npm package predating the
   `license` field), and a neighbouring release almost always carries the
   answer. When this happens the report says so on the package's line, and the
   result is deliberately not cached.

Python metadata gets one extra rule. PEP 639's `License-Expression` is SPDX and
wins outright. The legacy free-text `License:` field is trusted only if it is
short *and* names a license we recognize — values like `Dual License` or
`Other/Proprietary` say nothing, and the trove classifiers
(`License :: OSI Approved :: BSD License`) then carry the real answer.

A package whose license cannot be established by any of these routes is
reported as `unknown`, never assumed benign. "We could not tell" and "it is
fine" are very different answers to a licensing question.

## How a license is classified

License strings are parsed as **SPDX expressions**, which is what makes dual
licensing come out right:

- `MIT OR GPL-3.0-only` → **permissive**. We may take the MIT option.
- `MIT AND GPL-3.0-only` → **restricted**. Both sets of obligations apply.
- `MPL-2.0 AND (Apache-2.0 OR MIT)` → **weak-copyleft**.

`OR` takes the best branch, `AND` takes the worst. A gemspec `licenses` array,
npm's deprecated `licenses` list, and multiple PyPI license classifiers are all
the convention for dual licensing, so they are evaluated as a disjunction.

Non-SPDX free text (`Apache Software License`, `GNU General Public License v3
(GPLv3)`, `Ruby's`) is normalized by the ordered regex table
`LICENSE_PATTERNS`. **The ordering is load-bearing**: `affero` and `lesser` must
be matched before the generic `GPL` fallback, Boost's `BSL-1.0` before the
Business Source License's `BSL-1.1`, and npm's `UNLICENSED` (meaning
proprietary) before `Unlicense` (meaning public domain). `--self-test` runs 88
known-answer cases over exactly those traps; run it after touching the table.

GPL-family **license exceptions** are honoured, in both the modern
(`GPL-2.0-only WITH Classpath-exception-2.0`) and deprecated
(`GPL-2.0-with-classpath-exception`) spellings. A linking, Classpath, GCC,
autoconf or font exception removes the obligation that makes the base license a
blocker for a downstream consumer, so such a package drops to `weak-copyleft`
review rather than failing. An unrecognized exception does not.

### The four verdicts

| Verdict | Meaning | Examples |
| --- | --- | --- |
| `permissive` | Ship it. Attribution only. | MIT, BSD, Apache-2.0, ISC, Zlib, PSF, Ruby, CC0 |
| `weak-copyleft` | Review. Obligations attach to the dependency, not to COSMOS, provided we ship it unmodified and do not statically embed a modified copy. | LGPL, MPL-2.0, EPL, CDDL, Ms-PL, OFL, CC-BY-SA |
| `unknown` | Review. License could not be determined. | no metadata published |
| `restricted` | **Fail.** Incompatible with the Builder's License. | GPL, AGPL, SSPL, OSL, EUPL, QPL, Sleepycat, BUSL, Elastic-2.0, Commons Clause, CC-BY-NC, proprietary/`UNLICENSED` |

Note that `restricted` covers more than copyleft. A source-available or
non-commercial license (BUSL, Elastic, Commons Clause, `-NC`) is just as
unshippable, for a different reason.

## Responding to a finding

**`restricted`.** Remove the dependency, replace it, or obtain a commercial
license from its owner. If — and only if — it genuinely cannot taint a shipped
artifact, add an entry to `EXCEPTIONS` in the script:

```python
EXCEPTIONS: dict[str, str] = {
    "js:some-gpl-linter": "Build-time only; never linked into or shipped with "
                          "any COSMOS artifact. Reviewed 2026-01-01.",
}
```

Keys are `<ecosystem>:<name>` or `<ecosystem>:<name>@<version>`. The reason is
not optional, and the self-test enforces that it is non-empty. An exception
suppresses the *failure* only — the report still shows the package's real
verdict with `APPROVED BY EXCEPTION` beside it, because an exception is a
decision to accept a risk, not a claim that the license changed. Adding one is a
licensing decision and belongs in a reviewed commit.

**`unknown`.** Read the package's actual license file, then either fix the
upstream metadata (the durable fix, and usually a one-line PR) or record the
conclusion as an `EXCEPTIONS` entry citing where you read it.

**`weak-copyleft`.** No action needed to *use* the dependency as-is. Two things
to keep true: ship it unmodified, and do not copy its source into COSMOS. If we
ever need to patch one, that patch is subject to the dependency's license and
has to be published under it.

## Current state

Snapshot from 2026-09-03 (`--show all` for the full list):

- **1794 packages audited**, 335 of them reaching a shipped artifact.
- **0 restricted.** No GPL, AGPL, SSPL or non-commercial dependency anywhere in
  the tree, runtime or dev.
- **3 unknown**, all upstream metadata gaps rather than tool failures: the
  Python `iroh` 1.0.0 release publishes no license field at all, the Ruby
  `websocket-native` gemspec has an empty `licenses` array, and npm's
  `require-like` (dev-only, via the docs site) predates the `license` field.
  Each is worth a one-line upstream PR.
- **23 weak-copyleft**, 5 of them runtime: `psycopg`, `psycopg-binary` and
  `psycopg-pool` (LGPL-3.0-only), `certifi` (MPL-2.0), and `orjson`
  (`MPL-2.0 AND (Apache-2.0 OR MIT)`). All are used as unmodified installed
  packages, which is what LGPL and MPL are written to allow. The rest are
  `lightningcss` platform binaries and `gprof2dot`, which are build- and
  test-time only.

The `Ruby OR BSD` dual license that shows up on 28 runtime gems is the standard
Ruby-community dual licensing; the `OR` resolves permissive.

## Limitations, stated plainly

- It audits **declared** licenses. It does not read license *text*, and it
  cannot detect a package whose metadata is simply wrong. Metadata is what
  registries, distributors and every other license tool go on, and it is right
  the overwhelming majority of the time — but a finding of "0 restricted" is a
  statement about declarations, not a legal opinion.
- The version fallback answers with a *different release's* license. It is
  labelled in the report for exactly that reason.
- Runtime vs dev is computed from dependency graphs, which describe how packages
  were installed, not what a Dockerfile ends up copying into an image. Treat it
  as a strong hint, not proof.
- Copyleft obligations depend on how a dependency is combined with our code
  (dynamic use vs. static embedding vs. modification). The tool classifies the
  license; it cannot classify the linkage. That is why `weak-copyleft` is a
  review bucket and not a pass.
